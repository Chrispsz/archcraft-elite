## 2. Respostas diretas

### (a) Fluxo sha256sums — sim, há armadilhas (3 reais, 3 cosméticas)

**A1 — `grep -E part|ISO$` SEM aspas (bloqueia a verificação do usuário).**
``` 
sha256sum -c <(grep -E part|ISO$ sha256sums.txt)
``` 
Sem `'…'`, o shell interpreta `|` como **pipeline**: executa `grep -E part` e manda a saída para o comando `ISO$` → `command not found`. O `-c` recebe stream vazio → verificação "passa" sem verificar nada.
→ Fix: `sha256sum -c <(grep -E 'part|ISO$' sha256sums.txt)`

**A2 — case do `ISO$` (verificação parcial silenciosa).**
Se o nome real da ISO termina em `.iso` (minúsculo, padrão Archcraft), `grep -E 'part|ISO$'` case-sensitive **não seleciona a linha da ISO** → só as partes são checadas e o hash do ISO reassemblado nunca é validado, sem nenhum erro visível.
→ Fix: `grep -E 'part|\.iso$'` (ou `-Ei`) **e confirmar** o nome exato com `grep -n 'sha256sum --' .ci/build.sh` antes de fechar.

**A3 — glob no prefixo do `split` e no `cat` (ambiguidade que precisa de 1 linha de confirmação).**
``` 
split -b 1900M -d ISO ISO.part-*, rm ISO
...
sha256sum -- ISO.part-* >> sha256sums.txt
...
cat part-* > ISO
```
- Se `ISO.part-*` for **literal** no 3º argumento do `split`: os arquivos saem com `*` no nome (`ISO.part-*00`) → **nomes inextratíveis no Windows**; e num re-run com partes já existentes → `split: extra operand`.
- `cat part-* > ISO` não casa com prefixo `ISO.part-` → glob sem match, mas `> ISO` **cria/trunca a ISO mesmo assim** → arquivo vazio e `sha256sum -c` falha com hash errado (ou, pior, o usuário "conserta" desconfiando do hash).
→ Fix: `split -b 1900M -d ISO 'ISO.part-'` e `cat ISO.part-* > ISO`. *Preciso do excerto literal dessas 2 linhas para fechar se é paraphrase ou bug real.*

**Armadi­lhas cosméticas (não bloqueiam):**
- `sha256sum -- * > sha256sums.txt` num **re-run** com `out/` não limpo: o glob `*` inclui o `sha256sums.txt` antigo → hash auto-referencial órfão. CI é limpo por run → só afeta rerun manual.
- `>>` do `ISO.part-*` **duplica linhas** se o job de tag rodar 2×.
- A linha da ISO permanece no arquivo após `rm ISO` → `sha256sum -c sha256sums.txt` ingênuo falha por "arquivo ausente". É **intencional** (o usuário reassembla antes), e o JUNTAR-ISO.md cobre — mas vale uma frase explícita lá dentro.
- Ordem das linhas é irrelevante para `-c` ✅. Lexicografia de `ISO.part-*` = numérica até 99 partes (≈190 GB) ✅.

### (b) `gpu_cleanup_foreign` + `-Rns` — sem cascata legítima

- **`pacman -R` nunca remove dependentes**: se algo instalado ainda depender de um alvo, o pacman **recusa com erro** (não remove em cascata). O risco de `-Rns` é só o lado inverso — remover *deps folha* do alvo. As folhas de `nvidia-utils`/`nvidia-open` (`libxnvctrl`, `eglexternalplatform`, `lib32-*`, hooks alpm) são específicas da NVIDIA → inócuas no rig AMD, e vice-versa.
- **`vulkan-radeon`/`vulkan-intel` são dependentes de `mesa`, não o contrário** → remover não derruba `mesa`, `steam`, `vulkan-icd-loader` (todos seguem necessários). Allowlist nominais corretos.
- Os alvos Intel/AMD só existem como GPU discreta; 5700X e 5600 **não têm iGPU** → nada de "GPU gráfica oculta" sobrando dependente.
- **2 ressalvas de robustez (não de remoção):**
  1. Se o script roda sob `set -e` e o pacman **recusar** um alvo (dependente presente fora da allowlist), o script aborta no meio do firstboot → confirmar que cada `pacman -Rns` tem tratamento (`|| true`/`set +e` antes) ou que a re-checagem é o fallback.
  2. No Elite B, após remover `nvidia-open`, o `/boot/initramfs-linux-nvidia.img` gerado no live fica **órfão** → rodar `mkinitcpio -P` pós-limpeza. Cosmético (não é bootado no live), mas remove lixo.
