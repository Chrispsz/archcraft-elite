## 2. Diagnóstico (com evidência)

### (5) BUG REAL — `craft-pin-status` não-executável → módulo waybar morto em silêncio
O log do probe da sessão (verify) repete, a cada poll da waybar:
```text
2026-10-24T13:24:59.6012750Z BARS| sh: line 1: /usr/local/bin/craft-pin-status: Permission denied
2026-10-24T13:24:59.6013144Z BARS| sh: line 1: /usr/local/bin/craft-pin-status: Permission denied
```
(~12 ocorrências entre 13:24:59.6012750 e 13:24:59.6311238)

O formato `sh: line 1: <path>: Permission denied` é o `sh -c` que a waybar usa no `exec:` do módulo custom: o shell tenta `execve()` no arquivo e recebe **EACCES (exit 126)** — ou seja, o binário **existe mas não é executável** pelo `liveuser` (modo 0644, quirk clássico de `install`/`cp` sem `-m 0755`). É exatamente a **mesma classe** do fg-booster/xdotool da v1.5.2: uma dependência some/perde bit e o módulo morre sem derrubar a sessão.

E o gate que deveria pegar isso passou **verde**:
```text
2026-10-24T13:24:59.6056730Z ! grep -qE 'code=203/EXEC|Unable to locate executable' serial-verify.log
2026-10-24T13:24:59.6208843Z ✔ binários Elite executáveis (sem 203/EXEC — fix [9b] verificado)
```
`203/EXEC` é erro de **systemd** (unit ExecStart). Um módulo waybar executado via `sh` **não gera 203/EXEC**, gera `EACCES`/126. Por isso o gate "binários Elite executáveis" fica verde enquanto um `/usr/local/bin/craft-*` está literalmente inexecutável. **Falso-verde.**

## 4. Correção proposta

### 4.a — Build: garantir `+x` nos helpers Elite (patch na origem)
Onde o overlay instala os `craft-*` em `/usr/local/bin`, fixar modo (ex.: `install -Dm0755 …`) e, como rede de segurança, uma varredura no `elite/fragments/elite-customize.sh` (ou no fim do `apply-overlay.sh`):
```bash
# v1.8.2: módulos waybar chamam craft-* via sh → EACCES se não for +x
# (gate [9b] NÃO pega isso: 203/EXEC é systemd, não sh/126)
while IFS= read -r -d '' f; do
  [[ -x "$f" ]] || { chmod 0755 "$f"; echo "chmod +x $f (não-executável → EACCES na waybar)"; }
done < <(find /usr/local/bin -maxdepth 1 -type f -name 'craft-*' -print0)

# prova de evidência (entra no log da build)
stat -c '%a %n' /usr/local/bin/craft-* || true
```

### 4.b — Gate [9b]: caçar EACCES, não só 203/EXEC (no workflow `verify`)
Diff mínimo no passo "GATE — veredito do boot":
```diff
- ! grep -qE 'code=203/EXEC|Unable to locate executable' serial-verify.log
- chk $? "binários Elite executáveis (sem 203/EXEC — fix [9b] verificado)" "203/EXEC no live: binário 0644 no squashfs"
+ # 203/EXEC = systemd; EACCES = sh chamando binário não-executável (módulo waybar).
+ # v1.8.1: craft-pin-status passou VERDE aqui e morreu 12× como 'Permission denied'.
+ ! grep -qE 'code=203/EXEC|Unable to locate executable|/usr/local/bin/[^ :]+: Permission denied' serial-verify.log
+ chk $? "binários Elite executáveis (sem 203/EXEC e sem EACCES em /usr/local/bin)" "203/EXEC ou EACCES: binário não-executável no squashfs (ver BARS| acima)"
```

### 4.c — Gate barato de build (falha ANTES da ISO nascer)
No `elite-customize.sh`, abortar se houver `craft-*` sem bit de execução:
```bash
bad=$(find /usr/local/bin -maxdepth 1 -type f -name 'craft-*' ! -perm -u+x | tr '\n' ' ')
[[ -z "$bad" ]] || { echo "ELITE-FAIL: helper Elite sem +x: $bad" >&2; exit 1; }
```

## 5. Riscos

- **4.a (`chmod +x` em `craft-*`)**: se algum `craft-*` for dado (config, não script), o `+x` é inócuo. `find -type f` ignora symlinks — se algum helper for symlink para alvo não-exec, o patch não o cobre (usar `-L` se for o caso). Baixo risco.
- **4.b (gate EACCES)**: ampliar o blocklist pode gerar falso-positivo se houver `Permission denied` benigno (AppArmor/SELinux) em dmesg. Mitigado por ancorar o padrão em `/usr/local/bin/…: Permission denied`. Se surgir falso-positivo, escopar mais (só linhas `BARS|`).
- **4.c (fail no build)**: transforma um defeito hoje silencioso em build vermelha — é o objetivo, mas exige que o overlay realmente corrija o modo antes de reativar o gate, senão vira fail-loop.
- **Não mexi**: o selo `file:///tmp/pf-db/sync` e o fallback de preflight estão saudáveis nesta run (zero curl no pacstrap) — mexer neles seria regressão.
- **Limite de evidência**: sem o serial de uma run anterior não dá para **provar** se `craft-pin-status` regrediu agora (v1.8.1, "debloat sistêmico") ou se já vinha quebrado. O log só prova que **está** quebrado agora. Não afirmo regressão sem o serial de comparação.
